# Lot/Serial and Product Genealogy

Implements the traceability data/API slice for SRS v2.1 FR-WMS-02, FR-WMS-06, FR-WMS-07 and FR-WMS-09, connecting to the existing inventory stock ledger, posted GRN and production reports.

## Data model and controls

- `traceability_units` registers material/finished-good lots, individual serials, cartons, pallets, bundles and shipment identities. Unit code/barcode are unique case-insensitively per factory; a serial always has quantity 1.
- Material identities may link to an accepted line of a **posted GRN**. The database validates factory scope, derives the inventory item and supplier from the receipt/PO, and prevents registered lot/serial quantities from exceeding the accepted quantity or mixing bulk and serial representations.
- Finished-good identities may link to an order production report. The database binds the order and line from the report and prevents represented good quantity from exceeding reported output. Each report is represented by a bulk/lot identity or serial identities, not both.
- `product_genealogy_events` is an append-only directed graph supporting consumption, processing, split/merge, rework, carton/pallet packing and shipment relationships. Database guards reject cycles, cross-factory links, excessive cumulative source quantity, invalid source status and allocation-policy violations.
- `traceability_unit_status_events` preserves versioned quarantine, recall, disposition and shipment status history. Identity/provenance is immutable; status changes need a reason plus audit/outbox evidence.
- `traceability_label_templates` defines tenant/factory-specific QR, Code 128, Data Matrix or GS1-128 layouts for supported identity types. Issued traceability-unit and inventory-material label payloads snapshot lifecycle `status`; traceability labels can expose quarantine, recall or shipped state, while new material labels are rejected for inactive items. Clients can use these snapshots for print-preview handling indications. The API stores issued label snapshots. The client workbench at apps/web/src/lib/wms-label-renderer.mjs currently generates local QR and Code 128 B SVG and browser HTML print payloads, validates identity/status snapshots when a current identity is supplied, and fails closed for Data Matrix and GS1-128 until their encoders are implemented. Physical printing, scanner/device compatibility and site acceptance remain separate gates; see docs/wms-mobile-offline-label-acceptance.md.
- `traceability_settings` configures retention (1–100 years; default 7) and FIFO/FEFO/lot/serial material consumption policy.

## Material FIFO/FEFO candidate ordering and reservation evidence

The inventory reservation allocator resolves allocation policy from the most-specific applicable scope: material, then sector, then factory, then `traceability_settings` (FIFO is the final default). FIFO orders eligible LOT/SERIAL stock by the GRN's `posted_at`, then `received_at`, falling back to the identity's `created_at`; FEFO orders by earliest non-null expiry first, then that same receipt timestamp as its tie-break. Stable unit code, location and identity keys finish the ordering. A null expiry is placed after dated expiries for FEFO.

Candidates are restricted to ACTIVE material identities with unexpired or no expiry, positive unreserved tracked quantity, and an active picking-enabled BIN below an active WAREHOUSE/STAGING parent. Damaged, held, quarantined and EXPIRED condition flags are excluded, as are identities under an active item- or lot-scoped quality hold. Each candidate balance and identity row is locked during planning; the reservation transaction also locks the inventory item before planning and persists selected per-lot allocations with aggregate/BIN reservations in the same transaction. A changed per-lot availability predicate aborts the reservation rather than oversubscribing stock.

The PostgreSQL integration regression `services/api/src/inventory/inventory.reservation.integration.spec.ts` now proves material FIFO precedence over sector FEFO using two inventory-linked lots in one BIN: the earlier-received lot has the later expiry, yet is allocated first. Two concurrent requests each demand four units from six available units; only one commits, and persisted reservation, lot, BIN and aggregate balances prove that no second reservation over-allocates the lots. The separate FEFO scenario exercises earliest-expiry selection and invalid-lot exclusions. Reservation excludes that otherwise-pickable identity; persisted assertions verify its audited status event, retained 0.5000 on-hand / 0.0000 reserved BIN balance, zero reservation allocations against it, and reconciled valid-LOT, BIN and aggregate balances after partial and work-order issue. Exactly one commits; persisted allocation order proves that the earlier-received lot is selected first, and per-lot, BIN and aggregate balances reconcile. All traceability tables force tenant RLS. Composite foreign keys keep source evidence within tenant/factory scope, API mutations use Idempotency-Key where applicable, and identity/status/genealogy writes require transactional audit and outbox evidence.

## API

All routes require authenticated actor, tenant and factory context plus the named IAM permission and factory-scope guard.

- `POST /api/v1/traceability/units` — register a material/finished-good lot, serial, carton, pallet, bundle or shipment identity; requires `traceability.write` and `Idempotency-Key`.
- `GET /api/v1/traceability/units?search=&unit_type=&product_role=&status=&limit=50` — search/filter identities; requires `traceability.read`.
- `GET /api/v1/traceability/units/:unitId` — read identity with GRN/supplier, inventory, production/order and label-template references.
- `POST /api/v1/traceability/genealogy` — add a directed relationship with source, target, quantity, notes and evidence JSON; requires `traceability.write` and `Idempotency-Key`.
- `GET /api/v1/traceability/units/:unitId/forward?depth=5&limit=200` — follow downstream batches, products, packaging and shipment identities.
- `GET /api/v1/traceability/units/:unitId/reverse?depth=5&limit=200` — follow a finished product/carton/shipment upstream to source lots and production identities.
- `GET /api/v1/traceability/units/:unitId/recall-impact?depth=5&limit=200` — build a bounded, read-only recall impact assessment with downstream identities, matching WMS customer shipments, latest delivery/POD reference metadata and upstream provenance. The response exposes node/depth truncation indicators.
- `POST /api/v1/traceability/units/:unitId/recall` — declare an auditable recall case from a complete bounded downstream graph; requires `traceability.write`, a reason and `Idempotency-Key`. Truncated graphs fail closed without status changes.
- `POST /api/v1/traceability/units/:unitId/status` and `GET /api/v1/traceability/units/:unitId/status-history` — controlled state changes plus immutable history.
- `POST /api/v1/traceability/label-templates`, `GET /api/v1/traceability/label-templates` — create/read label templates.
- `GET /api/v1/traceability/settings`, `PUT /api/v1/traceability/settings` — read/update factory retention and allocation policy using optimistic `expected_version`.

Forward/reverse/recall-impact queries cap depth at 12 and nodes at 500. Relationship `evidence` JSON can hold external quality certificate, inspection and shipment references.

A declared recall is persisted by migration 205. The API acquires the same tenant/factory graph lock used by genealogy writes, traverses the downstream graph breadth-first, locks all affected identities and refuses to write when depth, node or per-layer fan-out limits prevent a complete traversal. A successful declaration inserts an immutable `wms_traceability_recall_cases` record and its unit snapshots, then transitions `ACTIVE`/`QUARANTINED` identities to `RECALLED` with versioned status history, audit and outbox evidence in one transaction. An exact retry returns the original case; reuse of the key with another reason or bound conflicts. The case snapshots a deterministic graph fingerprint and per-unit depth/status/action.

The existing unit lifecycle does not permit `SHIPPED` to transition to `RECALLED`; shipped identities remain `SHIPPED` and are explicitly marked `SHIPPED_REVIEW_REQUIRED` for separate customer/site action. Already-recalled and disposed units are captured without an extra status transition. Declaring a case changes neither inventory balance nor stock movements and does not dispatch stop-ship commands, notify customers, or capture acknowledgements. Authorized recall-owner approval, customer contact, containment and site acceptance remain separate gates.

The recall-impact endpoint requires `traceability.read` and uses the authenticated tenant/factory scope. It never changes stock or identity status and creates no recall record; the response explicitly reports these side effects as false. The response distinguishes `impact_node_limit_reached` / `provenance_node_limit_reached` from `impact_depth_truncated` / `provenance_depth_truncated`; the combined `impact_truncated` and `provenance_truncated` flags are true when either limit prevents a complete traversal. Treat any truncation as an incomplete assessment and rerun with appropriate bounded parameters before deciding recall scope. Recall declaration, quarantine/stop-ship decisions, customer notifications/acknowledgements and recall-owner acceptance remain separate operational actions and are not implied by this preview.

## Work-order production output genealogy (migration 198)

For new work-order output reports, the output-posting transaction now creates a LOT / FINISHED_GOOD traceability identity for positive accepted-good quantity and binds it through production_output_postings.traceability_unit_id. When scrap is positive, it creates a separate LOT / OTHER scrap evidence identity and binds it through scrap_traceability_unit_id; scrap identities have no inventory item and do not create sellable stock. The finished-good identity is assigned only to stock capacity in the existing default UNASSIGNED bucket, bounded by the item/location ledger and tracked-identity balances.

When a work order completes, the same transaction consumes its remaining material reservations and translates the immutable inventory_reservation_consumption_traceability_allocations rows into append-only product_genealogy_events. Material-lot quantities remain expressed in the source UOM and are deterministically apportioned across reported good/scrap output by integer four-decimal arithmetic. A serialized source identity is kept whole and linked to exactly one output target; when several output targets exist, its target is chosen deterministically by an output-weighted midpoint across the ordered serial allocations. Serialized material must retain its one-unit quantity. Matching audit and outbox evidence is inserted in the same transaction, and database constraints validate source/target scope, cumulative source quantity, cycle prevention and policy-order rules. Missing output identities or malformed serialized quantities fail the completion transition closed instead of reporting complete without the required traceability.

Migration/contract: migrations/198_production_output_lot_genealogy.sql and services/api/test/production-output-lot-genealogy.sql. Unit tests cover good + scrap identity creation, scrap-only handling and exact consumption-quantity conservation across multiple output reports.

Migration 199 makes this linkage a PostgreSQL invariant, not just an API convention. A genealogy edge into a work-order finished-good or scrap output must bind to an actual `inventory_reservation_consumption_traceability_allocations` row whose reservation belongs to that same work order and whose source lot/serial and output posting/report match. The database rejects arbitrary evidence JSON, checks the edge quantity against the allocated source quantity, and uses deferred constraints to require exact allocation conservation and a `COMPLETED` work order at commit. A work order cannot complete while any consumed tracked material allocation is missing from output genealogy. PostgreSQL acceptance is `services/api/test/work-order-genealogy-consumption-guard.sql`; the ordered manifest and CI replay migration 199 twice.

The production-report-to-output-lot slice deliberately does not backfill historical output quantities into current physical bins. Migration 201 separately closes a bounded carton/pallet packing and customer-dispatch backend slice. The WMS mobile queue now has a durable browser IndexedDB client workbench and server receipt-gated cleanup tests; RFID HIL, recall-owner acceptance and live plant end-to-end rehearsal remain open.


## Carton/pallet packing and customer dispatch (migration 201)

- `POST /api/v1/traceability/containers` creates a carton or pallet identity bound to an active item, a pick-enabled BIN/STAGING location and declared capacity.
- `POST /api/v1/traceability/containers/:containerUnitId/contents` records finished-good lot quantities into cartons or whole sealed cartons into pallets. The immutable `PACKED_INTO` genealogy edge, content row and capacity counter commit together; a carton cannot be nested into more than one pallet.
- `POST /api/v1/traceability/containers/:containerUnitId/seal` seals a non-empty container with an idempotent seal record. Sealed containers cannot accept further contents.
- `GET /api/v1/traceability/shipments?search=...` lists shipments in the authenticated factory and can filter by shipment code, customer name, customer-order reference or carrier tracking reference, so the dispatch is queryable without guessing an identity UUID.
- `POST /api/v1/traceability/containers/:containerUnitId/dispatch` dispatches one sealed carton/pallet to an identified customer and external customer-order reference. The transaction expands package genealogy to finished-good lot leaves, checks item/UOM/location, expiry, quality holds and unreserved stock, issues aggregate and lot-location stock, inserts immutable inventory ISSUE evidence, creates the shipment identity and `SHIPPED_AS` edge, updates shipped statuses, and commits audit/outbox evidence.
- Migration 201 adds tenant RLS, append-only packing/shipment records, database guards for source/container type and capacity, exact packed-quantity reconciliation, shipment-to-inventory-movement binding, and deferred shipment genealogy/status/audit/outbox evidence. Active carton contents also become stock commitments: deferred guards on aggregate, bin and lot balances stop later reservations, transfers or issues from consuming committed packed quantity. Shipment atomically releases the commitment when it marks the package dispatched and posts the stock issue. PostgreSQL CI replays the migration/SQL contract twice and exercises carton → pallet → customer dispatch, idempotent dispatch, and rejected stock depletion beneath an active packing commitment.

**Boundary:** this slice supports one sealed carton or pallet per shipment record and stores the external customer order reference supplied by the caller. It does not claim an internal ERP sales-order/customer-master integration or carrier certification. Client QR/Code 128 rendering and the durable offline queue are documented in docs/wms-mobile-offline-label-acceptance.md; the dispatch backend slice does not itself certify these clients or physical printers/scanners, RFID HIL, or plant acceptance.

## Internal customer-order binding and delivery evidence (migration 202)

- `POST /api/v1/traceability/containers/:containerUnitId/dispatch` optionally accepts both `order_id` and `order_line_id`. If either is supplied without the other, dispatch is rejected. The order must belong to the same tenant/factory and be in a dispatchable status; customer name and order reference must match the order, and the order line's SKU/UOM must match the finished-good item.
- Partial shipments are permitted, but shipped quantities for the bound order line are serialized and summed; the dispatch is rejected if it would exceed the line quantity. Migration 202 enforces this again inside PostgreSQL, in addition to API validation. Existing external references remain supported for backward compatibility, so unbound shipments must not be reported as ERP-validated orders.
- Carrier metadata is optional for legacy/external dispatches, but `carrier_name` and `tracking_reference` must be supplied together. Migration 204 enforces that invariant and prevents duplicate tracking bindings within a tenant/factory using case-normalized carrier and tracking identity. Signed carrier webhook lookup uses the same normalization, so a callback cannot ambiguously select between case-differing duplicates.
- `POST /api/v1/traceability/shipments/:shipmentUnitId/delivery-events` appends idempotent delivery lifecycle events (`IN_TRANSIT`, `OUT_FOR_DELIVERY`, `DELIVERY_FAILED`, `DELIVERED`, `RETURNED`). Invalid transitions and post-delivery/post-return events are rejected. `DELIVERED` requires a recipient, proof type, relative object-storage key, SHA-256 digest and signed timestamp. Events are append-only, forced-RLS scoped and committed with audit/outbox evidence; the list endpoint exposes the delivery timeline and latest event on the shipment search response.
- Delivery-event idempotency fingerprints the normalized caller payload: if `event_at` is omitted, the server assigns the timestamp on first insert, but an identical retry replays that original event and timestamp. A changed payload under the same key conflicts; server-generated clock values do not turn a matching retry into a different request.
- PostgreSQL acceptance is `services/api/test/wms-shipment-delivery-order.sql`; the full integration test covers order/SKU/UOM/customer binding, over-shipment rejection without stock loss, delivery-event idempotency, mandatory POD metadata, terminal-state rejection, and tenant isolation. CI applies and re-applies migration 202 and its structural contract.

**POD integrity boundary:** `POST /integrations/wms/shipments/:shipmentUnitId/pod-object` accepts one bounded JPEG, PNG or PDF, verifies its byte signature against the declared media type, writes it to configured S3-compatible object storage under `pod/{tenantId}/{factoryId}/{shipmentUnitId}/{objectId}`, then performs an independent GET and recalculates SHA-256 and byte length over the stored bytes. It returns the scoped `proof_reference` and verified `proof_sha256`. Before a first `DELIVERED` event is committed, the manual lifecycle service and signed `WMS_CARRIER` webhook both require the key to match the shipment resolved within the exact tenant/factory scope and re-read the object to verify the claimed digest. Missing configuration/object, cross-shipment keys, access failures or digest mismatch fail closed. An exact existing idempotency replay returns the already-committed event without a redundant storage round-trip. API CI runs the upload/read-back path against an isolated RustFS S3-compatible server. 

**Remaining boundary:** this is verified digital POD object storage, not proof that a carrier physically completed delivery or that the recipient/signature is genuine. Signed carrier webhooks are authenticated by the configured connector secret, while live provider certification and operational sign-off are still required. Physical scanner/printer rendering, RFID/offline shipping scan integration and live plant acceptance remain open and require provider/device/site evidence.

## Serial indivisibility and fail-closed stock transformations (migrations 236, 238)

SRS v2.1 FR-WMS-04 requires serial allocation to preserve the individual physical identity. Migration `236_wms_serial_indivisibility.sql` makes that rule a PostgreSQL invariant, not only an API convention:

- A SERIAL source or target can appear on a genealogy edge only with quantity exactly `1`. A SERIAL cannot be split as a source or collapsed by `MERGED_INTO`; a serial target can have only one `SPLIT_INTO` parent.
- **A LOT-to-SERIAL genealogy edge is not an inventory split.** Migration `238_wms_genealogy_transformations_require_commands.sql` now rejects every new `SPLIT_INTO` and `MERGED_INTO` write from the generic genealogy path, including direct SQL. A transformation is unavailable until a dedicated command atomically conserves aggregate stock, location/bin balances, traceability-unit balances, reservations and immutable audit/outbox evidence.
- A serial's on-hand and reserved location balances are each strictly `0` or `1`, and the sum across **all** locations for that serial cannot exceed one. The serial identity row is locked while those balances change, so concurrent moves cannot claim the same unit at two locations.
- A SERIAL reservation must be backed by exactly one on-hand unit and one reserved unit in the same location. Only one outstanding allocation is permitted; partial issue and partial release are rejected, consumed serials cannot be allocated again, and consumption evidence must record exactly one unit once.
- A location transfer carrying a SERIAL must move exactly one unit. Lot-level partial reservations, issues and transfers remain supported.
- Before installing the guards, migration 236 checks existing genealogy, location, reservation, consumption and transfer rows. Any legacy fractional or duplicated serial state blocks deployment for audited reconciliation rather than being silently accepted.

The migration uses row locks for serial-specific balance, reservation, consumption and transfer writes, and shares the canonical genealogy graph lock before locking genealogy endpoints. Migration 238 takes a write lock while installing the new barrier and fails deployment preflight if historical split/merge edges exist, so they require explicit owner-audited reconciliation rather than silent grandfathering. The generic API rejects these relationship types before opening a transaction; the database trigger independently rejects direct inserts. PostgreSQL CI applies and replays migration 238 before `services/api/test/wms-serial-indivisibility.sql`, which proves LOT-to-SERIAL split and LOT-to-LOT merge attempts leave genealogy, aggregate, BIN and identity stock unchanged. The guard itself does not implement stock transformations; dedicated authenticated stock-conserving LOT/SERIAL commands are implemented in migrations 241/242 below.

A second, isolated PostgreSQL integration scenario in `services/api/src/production/production-work-orders.multi-operation.integration.spec.ts` registers one MATERIAL SERIAL (quantity exactly 1) in an active picking BIN, creates two independent approved three-step work orders requiring that same component, and races their RELEASE commands. Exactly one work order obtains the sole serial reservation; the other fails closed without a material-reservation child. The winning order traverses cutting → assembly → finishing, reports and replays one output idempotently, completes, consumes the full serial once, and records exactly one `CONSUMED_INTO` edge of quantity 1 from the source SERIAL to the generated FINISHED_GOOD LOT using the weighted-midpoint single-target rule. That same fixture now requests one explicit finished-good SERIAL output (exactly one accepted good unit) and asserts the exact serial code, output identity type, unique output posting/report, idempotent replay and one-unit traceability-location balance; the final edge is SERIAL-to-FINISHED_GOOD-SERIAL `CONSUMED_INTO`. Persisted checks reconcile the source serial identity/location, BIN and aggregate balances to zero on-hand and zero reserved, the consumed reservation, the single consumption allocation, and the finished-good serial balance to one on-hand / zero reserved. This proves a bounded tracked-SERIAL material-input to finished-good-SERIAL output path and competing release exclusion; it does not prove multi-serial distribution across mixed good/scrap batches, true manufacturing LOT/SERIAL split/merge commands, external provider/site operation or physical-device HIL.

A finished-good SERIAL can now be created directly from a work-order output report by supplying `finished_good_serial_code`. The API normalizes the code, binds it into the output idempotency fingerprint, and permits this mode only when `good_quantity` is exactly `1.0000`; callers report each finished-good serial separately. The production receipt creates a `SERIAL` identity with `product_role='FINISHED_GOOD'`, binds its one-unit traceability balance to the same default virtual location as the aggregate receipt, and links it to the exact production report/order line. Migration `237_production_finished_good_serial_output.sql` changes the output-posting trigger to accept either the existing bulk `LOT` identity or a one-unit `SERIAL`, while migration 199 continues to require each consumed material allocation to be fully represented by immutable output genealogy. The PostgreSQL integration scenario now verifies a SERIAL material input consumed into a SERIAL finished-good output, the exact serial code/quantity, the single output posting and the one-to-one genealogy edge; it also rejects a multi-unit serial output request. Bulk outputs without a serial code continue to create a finished-good LOT.

This is a bounded one-serial-per-output-report compatibility path. Additive multi-SERIAL output with mixed scrap is implemented by migration 240; authenticated stock-conserving material LOT split/merge and active reservation remapping are implemented by migrations 241/242. Representative external provider/site rehearsal, physical label printer/scanner/RFID/mobile HIL, partial-parent remainders, cross-location movement and independent owner/reviewer acceptance remain open. Physical scanner, RFID reader, printer and plant acceptance are separate hardware/site gates and are not implied by these tests.

## Stock-conserving LOT transformation commands

Migration 238 still blocks generic SPLIT_INTO and MERGED_INTO genealogy writes. Migration 241 adds dedicated factory-scoped, permission-gated commands. A split accepts one material LOT and creates 2–100 LOT and/or whole-unit-SERIAL children, with explicit per-location allocations. Mixed LOT/SERIAL child sets are allowed only when the effective material policy is FIFO or FEFO; explicit LOT/SERIAL policies retain homogeneous output requirements. A merge accepts 2–100 compatible material LOTs and creates one new LOT. Sources must be active, unexpired, undamaged, unheld, quality-clear, unreserved and fully reconciled to unconsumed on-hand quantity. Reserved-source remapping, mixed child types, partial remainders and cross-BIN physical moves are not implemented.

Each event carries a transformation_id FK and must exactly match the immutable command line total for its source/target pair. The command moves only traceability identity-map quantities; it preserves each source BIN total and aggregate/item location ledgers, and preserves effective GRN receipt timestamp precedence in child identities for FIFO/FEFO allocation. Source LOTs transition to DISPOSED with status history; child identities receive registration audit/outbox; command and genealogy each have transactional audit/outbox evidence. services/api/test/wms-serial-indivisibility.sql proves a real two-LOT merge, ten-serial split, idempotent replay, late-write rollback and stock-conservation assertions. Migration 242 also remaps active reservation allocation remainders onto transformed LOT identities in the same transaction. The remap history preserves the consumed/released history, records source-to-target allocation evidence and inserts child allocations in the original per-reservation relative FIFO/FEFO order; subsequent issue evidence stores the exact replacement allocation row ID and issue-time sequence, so consumed quantities can be traced through the remap ledger to the original source allocation; subsequent release operates on replacement rows. WP02 and FR-WMS-02/04/09 remain PARTIAL / OPEN / NOT_ACCEPTED pending partial-parent remainder support, physical cross-location movement/put-away, complete forward/reverse recall acceptance, representative site/provider rehearsal, device HIL, capacity/recovery and independent owner/reviewer acceptance.


A dedicated material-scope precedence regression now proves MATERIAL=FIFO overrides both SECTOR=FEFO and FACTORY=FEFO in one tenant/factory. It creates a unique factory and sector, two independent suppliers, two approved purchase orders and POSTED GRNs, then tracks two 3-unit material LOTs in one active pick-enabled BIN.
