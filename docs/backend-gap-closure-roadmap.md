## Rules for closing work

1. Work in medium-sized, reviewable slices. Each slice names its SRS requirement(s), owning HLD service/work package, migration impact, direct code tests, PostgreSQL contract, and exact-SHA CI evidence.
2. Keep the promotion path `rakibul-hasan` → `dev` → `main`. Do not promote a failed or unverified candidate, and never force-push shared branches.
3. Distinguish repository implementation from staging/production acceptance. A passing unit test, SQL structure check, green CI, or runbook does not prove a live provider, plant, restored database, or production configuration was exercised.
4. A requirement can be marked PASS only after its current SRS wording/priority is reconciled, direct code/migration/test evidence is linked to the candidate SHA, and any required operational evidence and named owner/reviewer approval are recorded.
5. Do not convert the 950 cumulative scope count, the 899 extracted-ID index, or the 37 source-priority review entries into a completion percentage. The source/priority denominator needs owner-attested reconciliation first.

## Current slice and next completion gates

### Step 1 — read-only inventory stock summary

**Implementation target:** `INVENTORY.STOCK.SUMMARY@1.0.0`.

- Reads only the authoritative aggregate inventory balance for one item.
- Calls the existing Inventory domain service, not a caller-supplied query or arbitrary URL.
- Rechecks `inventory.read` through IAM; the SQL query has explicit tenant/factory/item predicates and uses transaction-local RLS context.
- Requires a strict item UUID schema and returns balance quantities as decimal strings plus a balance version.
- Performs no stock mutation. Missing scoped item returns a bounded failure; an absent executor stays fail-closed.
- Adds the tool to the ordered migration manifest and requires API unit tests plus a PostgreSQL registry contract before promotion.

### After Step 1

1. Verify the new executor on the feature PR's exact SHA with API CI and PostgreSQL CI.
2. Promote through `rakibul-hasan` → `dev` → `main` only after checks pass.
3. Refresh WP06/SRS evidence without marking the whole AI runtime accepted.
4. Take the next medium-sized slice from WP02 WMS end-to-end evidence, then proceed by the ordered dependencies above.

### WP02 slice — finished-good lot put-away and directed movement

**Gap:** production output creates a finished-good lot in traceability, but directed inventory movement treated every supplied identity as a raw-material LOT/SERIAL and did not return `traceability_unit_id` to API callers. An identity could also be omitted from a generic move when the tracked stock at the source was a finished-good lot.

**Implementation/acceptance:** migration 200 adds a database guard for scoped, active material LOT/SERIAL and finished-good LOT identities, rejects tracked movements without an explicit identity, and blocks active quality-held/expired/damaged stock. The location service now transfers finished-good lot balances with the aggregate per-location balances and returns the selected identity in API results. Unit/PostgreSQL integration coverage checks put-away from UNASSIGNED to BIN, BIN-to-BIN transfer, BIN-to-STAGING pick, idempotent replay, aggregate/location/identity quantity conservation, and missing-identity rejection. Migration 200 is part of the explicit manifest and its SQL contract is re-run to test migration idempotency.

**Boundary:** this closes the backend directed-movement identity gap for the supported finished-good LOT. It does not claim carton/pallet shipment capture, scanner/RFID hardware acceptance, production-site deployment, or completion of all WP02/SRS requirements.

### WP02 slice — internal customer-order binding and proof-of-delivery evidence

**Gap:** migration 201 dispatches a sealed carton/pallet to a caller-supplied customer and external order reference, but did not prove the shipment matched a FactoryOS customer order line or keep a durable delivery/POD timeline.

**Implementation/acceptance target:** migration 202 adds optional `order_id`/`order_line_id` binding to immutable shipment records and database guards that verify same tenant/factory, permitted order status, matching customer and order reference, matching finished-good SKU/UOM, and cumulative shipment quantity not exceeding the order line. Legacy unbound shipments remain accepted for compatibility and must not be described as ERP-validated. The delivery-event API stores append-only, idempotent lifecycle events and requires recipient/proof type/object-key/SHA-256/signed timestamp for `DELIVERED`; state transitions, RLS, actor scope, audit/outbox and migration replay are database-guarded.

**Direct regression/acceptance:** PostgreSQL integration covers order-line over-shipment rejection without stock loss, wrong customer rejection, successful exact-order binding, delivery-event replay, missing-POD rejection, valid POD evidence, rejection of events after terminal delivery and cross-tenant reads. `services/api/test/wms-shipment-delivery-order.sql` asserts the database columns, constraints, RLS and triggers; CI re-applies migration 202 and the SQL contract.

**Boundary:** migration 202 and the append-only event model preserve order binding, delivery lifecycle, RLS, actor scope, audit and outbox guards. The configured storage/digest verification is implemented in the subsequent WP02 slice below. Legacy shipments without internal order IDs remain compatible and are not ERP-validated. Configured carrier connectors reuse the existing signed-webhook ingress (raw-body HMAC, timestamp window, connector pause/secret-reference rotation, rate limiting and replay receipts) and append scoped WMS delivery events with audit/outbox evidence. A connector must be registered as `WMS_CARRIER`, approved/active, have a secret reference of at least 32 bytes, and allow `WMS.SHIPMENT_DELIVERY`; payloads must identify the carrier and unique tracking reference in the connector's tenant/factory. A `DELIVERED` event requires recipient, proof type, relative object key, SHA-256 metadata and signed timestamp. This closes code-level signature-to-ledger integration, not a real carrier sandbox certification. The durable IndexedDB client queue and QR/Code 128 browser SVG/HTML renderer are now implemented in the bounded web workbench and have automated client contracts. The browser renderer now supports a bounded GS1-128 profile with explicit AI allowlisting and field validation; Data Matrix encoding, native printer protocols, camera decode, physical scanner/printer compatibility, RFID/offline shipping capture and site/device acceptance still need their own implementation or evidence. This is one bounded WP02 slice, not acceptance of all WP02/SRS requirements.

### WP02 slice — signed carrier webhook to delivery ledger

**Gap:** generic signed integration webhooks had signature and replay controls but were stored only as integration outbox events; those accepted events did not advance the WMS shipment's append-only delivery timeline.

**Implementation/acceptance target:** only a `WMS_CARRIER` connector may submit the canonical `WMS.SHIPMENT_DELIVERY` event (and that connector is restricted to that event type). The mapper validates RFC 3339 event time, lifecycle values, carrier name and tracking reference, and for `DELIVERED` requires valid proof metadata; it resolves tracking only inside the connector tenant/factory and rejects missing or ambiguous matches. The WMS event, carrier receipt, integration outbox, WMS audit event and WMS outbox evidence commit in one PostgreSQL transaction. The carrier event uses its connector/event ID as an idempotency key and does not impersonate a human user; migration 203 makes non-human actor attribution explicit while preserving the manual actor guard and WMS lifecycle guard.

**Direct regression/acceptance:** integration service tests cover signed carrier event commit, missing POD rejection and factory-scoped tracking resolution. `services/api/test/wms-carrier-webhook.sql` asserts non-human actor handling and the active database guard; API PostgreSQL CI applies and re-applies migration 203 plus the SQL contract. Real provider payload compatibility and sandbox delivery/retry evidence remain provider-specific.

### WP02 slice — carrier/tracking identity integrity (migration 204)
**Gap:** dispatch allowed only one of `carrier_name` and `tracking_reference`, while signed callbacks require both to resolve a shipment. Distinct shipments could also reuse the same factory-scoped tracking identity with different letter casing, leaving webhook routing ambiguous.
**Implementation/acceptance:** dispatch rejects partial carrier metadata and non-printable/non-ASCII values. Migration 204 enforces the pair invariant in PostgreSQL and adds a unique tenant/factory index over normalized carrier name and tracking reference. The carrier webhook resolver uses the same case-normalized comparison, so dispatch uniqueness and callback lookup agree.
**Direct regression/acceptance:** the WMS PostgreSQL integration test rejects one-sided metadata and a second dispatch using the same case-insensitive carrier/tracking pair; the shipment's stock remains available for a later valid dispatch. `services/api/test/wms-carrier-tracking-integrity.sql` asserts the check constraint, valid unique index and registered migration. API PostgreSQL CI applies and re-applies migration 204 and runs the structural contract.
**Boundary:** this makes the local shipment binding deterministic; it does not certify a live carrier API or provide provider sandbox credentials.

### WP02 slice — configured POD object fetch and digest verification

**Implementation/acceptance:** the API uses SigV4 to retrieve a validated relative key from one server-configured S3-compatible bucket, bounds response size/time, rejects redirects and empty bodies, and independently computes SHA-256 before any WMS delivery business transaction. Only HTTPS is accepted for production storage endpoints. Exact accepted replays skip redundant object reads; payload conflicts continue through the signed-webhook receipt/reconciliation logic. Unit regression coverage exercises signing, success/mismatch, missing configuration, traversal keys, oversize content and production HTTPS; carrier integration coverage asserts a digest mismatch cannot write the WMS event or receipt. Operator setup and provider responsibilities are recorded in docs/wms-pod-object-storage-verification.md.

**Boundary:** this adapter is read-only. The carrier/provider must place the bytes at the agreed object key before callback; this code does not create upload URLs or upload the bytes. Actual storage credentials/bucket policy, provider sandbox certification, the bounded client slice now covers QR/Code 128 SVG rendering and receipt-gated IndexedDB offline queue; Data Matrix, native printer protocols, camera decode, physical device tests, live carrier certification and site commissioning evidence remain outstanding; GS1-128 now supports a bounded AI profile, which still needs independent device-decode verification. No real external storage was available to certify during this code change.

### WP02 slice — bounded read-only recall impact assessment
**Gap:** forward/reverse genealogy could be queried, but there was no single bounded operational response joining downstream identities to WMS customer-shipment/delivery evidence for recall triage.
**Implementation/acceptance:** `GET /api/v1/traceability/units/:unitId/recall-impact` uses `traceability.read` and authenticated tenant/factory scope. It returns the starting identity, downstream genealogy nodes/edges, matching WMS shipments with customer/order/tracking and latest delivery/POD reference metadata, upstream provenance and explicit truncation indicators. PostgreSQL acceptance covers a finished-good lot traced through carton/pallet paths to two separate shipments, conservative node bounds, no stock/status changes, and cross-tenant rejection.
**Boundary:** impact analysis only. It does not declare a recall, set RECALLED/QUARANTINED status, adjust stock, issue stop-ship commands, notify customers, capture acknowledgements or replace recall-owner/site acceptance. A truncated graph is not a complete recall assessment.

### WP02 slice — bounded recall declaration (migration 205)

**Gap closed in code:** the recall impact preview now has a separate, permission-gated declaration endpoint. It creates a durable recall case rather than making operators infer that a read-only preview itself enacted a recall.

**Implementation/acceptance:** `POST /api/v1/traceability/units/:unitId/recall` requires `traceability.write`, a non-empty reason and an `Idempotency-Key`; the optional depth/node bounds remain within 1–12 and 1–500. The transaction takes the same tenant/factory genealogy graph advisory lock used by graph writes, traverses downstream edges breadth-first, refuses layer fan-out or node-limit overflow and checks for unseen edges beyond the depth boundary before writing any case or status. It locks the selected identities in stable order, snapshots the graph fingerprint, and atomically inserts an immutable case plus membership snapshots, any applicable `RECALLED` status transitions/history, and matching audit/outbox evidence. Exact retries return the original case; a reused key with a different payload conflicts.

**Status boundary:** `ACTIVE` and `QUARANTINED` units transition to `RECALLED`; already-recalled and disposed identities are recorded as such. A `SHIPPED` identity remains `SHIPPED` because the existing state machine intentionally does not permit a shipment fact to be rewritten; the case marks it `SHIPPED_REVIEW_REQUIRED` for separate customer/site disposition. No stock quantity/movement is changed, and this endpoint does not issue stop-ship commands or send customer notifications/acknowledgements. Recall-owner approval, customer communication and site execution remain operational release gates.

**Evidence:** migration `205_wms_traceability_recall_execution.sql`, SQL contract `services/api/test/wms-recall-case.sql`, PostgreSQL integration for node/depth truncation fail-closed, atomic unit status/history, idempotent replay, tenant scope and stock conservation; workflow applies and reapplies migration 205 and its contract. Exact-head CI and independent review are required before promotion.

**Release status remains OPEN** until the source/priority reconciliation and all applicable release gates above have direct evidence and authorized review. This roadmap intentionally records external blockers as external rather than inventing acceptance.

### WP02 slice — recall notification intent and acknowledgement ledger (migration 206)

**Gap:** an audited recall case could identify affected units and shipped-unit follow-up, but there was no durable customer/site notification-intent ledger or acknowledgement record linked to a specific recall case.

**Implementation/acceptance:** migration 206 adds tenant/factory-scoped notification intents and a one-per-intent acknowledgement ledger. APIs require authenticated factory scope, `traceability.write` for writes, idempotency keys, constrained non-URL recipient references and explicit acknowledgement outcomes. Notification requests add an outbox event atomically with audit evidence; acknowledgements require an existing intent for the same case and recipient, and likewise commit append-only records with audit/outbox evidence. PostgreSQL checks cover RLS, immutable triggers, recipient binding, uniqueness and migration reapplication.

**Boundary:** `WMS.RECALL_NOTIFICATION_REQUESTED` is an intent, not confirmation that an external provider transmitted or delivered anything. The current acknowledgement source is `OPERATOR_REPORTED`; there is no external customer authentication, delivery receipt, automatic customer email/EDI/portal transmission, stop-ship command or recall-owner approval in this slice. Those remain explicit operational/provider acceptance gates.

### WP02 POD delivery-event integrity gate — SRS v2.1 FR-WMS-07/08

The storage adapter alone is not enough: the `DELIVERED` lifecycle now injects `WmsPodStorageVerifier` and independently reads the stored object before a first delivery-event insert. The accepted key must be under the exact normalized `pod/{tenant}/{factory}/{shipment}/` prefix, preventing one shipment from binding another shipment's object. The first event is denied if storage is unconfigured, the object cannot be read, or its actual bytes do not match the submitted SHA-256. Exact idempotent replays return the original event and do not make a needless storage round-trip. API CI's isolated RustFS test exercises actual PUT, separate GET, byte-length/SHA-256 acceptance and wrong-digest rejection; service regression checks scope enforcement and fail-closed behavior. The existing WMS mobile PostgreSQL suite separately tests concurrent same-payload replay, conflicting payload races, and one-stock-movement conservation.

The upload and verify code only establishes stored-byte integrity. It does not certify a real carrier, authenticate that a recipient signature is genuine, render/print a physical label, or prove external recall notification delivery; those remain separate acceptance gates.

### WP02 slice — live storage and carrier certification smoke harness

**Software implementation:** \`scripts/integrations/wms-provider-certification.mjs\` is a fail-closed live-configuration harness for a dedicated staging/sandbox API origin and already-\`DISPATCHED\` test shipment. It verifies the active \`WMS_CARRIER\` connector contract, anonymous and read-only user upload denials, authenticated POD upload through the deployment's configured S3-compatible adapter, independent read-back SHA-256/byte-length response, invalid FactoryOS HMAC rejection, a synthetic signed delivery callback, exact event replay returning the original receipt, and conflicting event-ID payload rejection. It writes a JSON evidence artifact without recording supplied access tokens or the webhook secret. \`scripts/integrations/wms-provider-certification.test.mjs\` covers environment fail-closed rules, signature construction, authorization probes, byte digest, replay/conflict expectations and secret redaction; API CI runs that contract suite when the script changes.

**How to run / guardrails:** follow \`docs/wms-provider-certification.md\`. The harness requires explicit \`sandbox\` or \`staging\`, HTTPS, both an \`inventory.write\` token and a read-only token, the configured connector secret, provider metadata, and explicit acknowledgement that a test POD object and delivery/reconciliation evidence will be created. Do not run it against production data. Provider secrets must be injected through an approved secret-management workflow; never commit credentials or attach raw credentials to the evidence pack.

**Acceptance status and limits:** this is a configured deployment smoke, not proof of a carrier-initiated callback. The signed callback is generated by the harness using the FactoryOS connector HMAC secret and must be labelled synthetic. A successful run establishes that the deployed API can use its configured storage credential to upload/read back a POD object and that the FactoryOS HMAC receiver accepts/idempotently replays its own contract. The harness does not call a vendor-specific carrier sandbox API, prove the callback came from the named carrier, inspect provider-console retries, inspect credential rotation/expiry, or test storage bucket-list/delete denial. The selected provider's IAM policy must be independently reviewed for dedicated-prefix \`PutObject\`/\`GetObject\` only as required and no broad list/delete/unrelated-bucket rights. A real carrier sandbox run, provider-originated signed callback/retry/replay evidence, credential lifecycle review, storage IAM export/policy review and storage/carrier/WMS owner sign-offs remain **OPEN**; do not mark live carrier certification or storage least privilege PASS based on the synthetic callback or contract test.
