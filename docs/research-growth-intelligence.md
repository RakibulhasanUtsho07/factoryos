# Research & Growth Intelligence backend

**Implementation state:** API and PostgreSQL governance foundations are implemented; full product-level Research/Growth Intelligence is not yet complete. The remaining integration/evaluation boundaries are listed at the end.

## Research API

- `POST /watchlists`, `GET /watchlists` and `POST /watchlists/:watchlistId/decision` manage tenant-scoped topic watchlists for sectors, technologies, processes, markets, sustainability and strategic questions. Query terms, inclusion/exclusion terms, and allowed source types are stored under forced RLS; activation/pause/retire events are auditable. Watchlists are configuration only and do not imply that an external crawler worker is running.

The tenant-scoped endpoints are under `/research`:

- `POST /sources` registers source metadata and rights/access claims. It starts `PENDING`; source text is always untrusted.
- `GET /sources` lists the tenant's sources and approved global references.
- `POST /sources/:sourceId/decision` records approve/reject/revoke decisions with a reason. Approval is blocked for restricted/unknown rights or missing documented rights.
- `GET /sources/:sourceId/rights-history` exposes append-only source/license/access snapshots to `research.review` reviewers. Metadata revisions and rights/access changes increment separate source/right version counters; previously queued/running work is blocked when its source revision or rights snapshot changes.
- `POST /sources/:sourceId/ingestion-jobs` queues an idempotent `METADATA_ONLY` or rights-permitted `FULL_TEXT` job. Creation captures source/rights snapshots and fingerprints. A repeated idempotency key returns the original job only for the same request hash.
- `GET /ingestion-jobs`, `POST /ingestion-jobs/claim-next`, `POST /ingestion-jobs/:jobId/checkpoint`, `POST /ingestion-jobs/:jobId/pause` and `POST /ingestion-jobs/:jobId/failure` provide tenant-scoped status, expiring worker leases, resumable metadata checkpoints, heartbeat, retry scheduling and explicit failure reasons. Each stage change creates an immutable timeline event; stale leases and out-of-date expected versions cannot overwrite a newer worker.
- `POST /ingestion-jobs/:jobId/extraction` persists a worker-reported extraction run and source-located claim candidates atomically. A separate `POST /ingestion-jobs/:jobId/extraction-items/:itemId/decision` endpoint requires `research.review`, records one immutable APPROVE/REJECT decision against the exact output and current source/right versions, and atomically writes audit/timeline events. Extracted claims cannot be approved until that review decision is APPROVE; the same rule is enforced at the PostgreSQL trigger boundary. It records extractor/schema version, worker-attested input digest, server-computed canonical output digest, source/right revisions, prompt/config hashes when supplied, model metadata and safety findings. Extracted claims remain `PROPOSED`; prompt-control/data-exfiltration indicators require review and never auto-approve a claim.
- `GET /ingestion-jobs/:jobId/extraction` is limited to `research.review` and returns the extraction run/item lineage, source locators, SHA-256 digests, safety flags and immutable reviewer decision without returning raw source snapshots or excerpt bodies.
- `GET /sources/:sourceId/content-purges` is limited to `research.review` and returns the append-only digest/reason/version log for excerpt purges; it never returns the erased excerpt.
- `GET /ingestion-jobs/:jobId/events` returns the immutable progress/failure timeline. Job outputs exclude raw source/rights snapshots; checkpoints are capped metadata-only objects and reject obvious raw-text/excerpt fields.
- `POST /sources/:sourceId/claims` creates a proposed claim only from an approved tenant source. Every claim has citation locator metadata; stored excerpts up to 4,000 characters are permitted only when the source's rights explicitly permit full-text storage.
- `GET /claims` returns tenant claims and approved claims from the global namespace. `POST /claims/:claimId/assess-evidence` and `GET /claims/:claimId/evidence-assessments` are reviewer-only (`research.review`) endpoints for version-bound deterministic evidence scoring, citation metadata validation and safety screening. `POST /claims/:claimId/evidence-assessments/:assessmentId/safety-decision` records an immutable CLEAR/REJECT decision with a reviewer reason for flagged items. Assessments and safety decisions are append-only; the suggested grade never approves a claim by itself. `POST /claims/:claimId/decision` requires the approver to supply the final A–D grade and a current consistent citation assessment; flagged items also require a current explicit CLEAR safety decision.
- `POST /claims/:claimId/links` records `SUPPORTS`, `CONTRADICTS` and `RELATED_TO` relationships without silently merging conflicting claims.
- `POST /releases` creates a sequentially versioned draft bundle from visible approved claims. `POST /releases/:releaseId/evaluate` persists an immutable, versioned contract-evaluation record with a content fingerprint, citation/rights/consistency checks and a conservative prompt-injection indicator. `POST /releases/:releaseId/promote` requires a passing evaluation attached to the unchanged draft, reruns the checks and requires reviewer safety and external regression-evidence attestations; promotion atomically activates the new version and marks the previous active version as superseded without rewriting its content. `GET /releases/:releaseId/history` returns tenant-scoped version history, the active pointer, channel revision and lifecycle events. `POST /releases/:releaseId/rollback` requires `research.review`, a reason and an older previously promoted version of the same release key whose current rights/evidence checks and original passing evaluation fingerprint still match.
- `POST /claims/:claimId/relevance` maps an approved research claim to a verified/inferred CBB node for the authenticated factory, with tenant evidence, counter-evidence, assumptions and validation plan. `POST /relevance/:mappingId/decision` approves/rejects the mapping.

Global rows are read-only to regular tenant sessions: RLS permits reading `tenant_id IS NULL` global research rows but only permits writes where `tenant_id` equals the current tenant. This prevents a tenant upload from being stored into the shared research namespace.

## Research evidence grading, citation consistency and adversarial safety

- Each tenant claim can receive a persisted assessment under rubric `research-evidence-rubric.v1`. The 100-point factors are citation consistency (25), source identity (15), authorship/publication date (10), methodology (15), dataset/material description (15), limitations (10), practical implication (5), and independent-source corroboration (5). Thresholds are A (85–100), B (70–84), C (50–69), and D (0–49); an invalid citation is always grade D.
- The rubric is a deterministic completeness/traceability heuristic, not a calibrated probability, an expert judgment, or a substitute for domain review. It exposes per-factor scores and explanations. Assessments snapshot current source/right versions and claim-field digests; PostgreSQL computes the SHA-256 fingerprint from the exact stored JSONB snapshot. Records are append-only and cannot be used after the source/right version changes. A new assessment is required after relevant metadata changes.
- Citation validation requires a precise page, section, paragraph or URL-fragment locator and a registered DOI/URL source identity. Explicit DOI/URL locators are compared to the registered source; malformed/mismatched identifiers are rejected and ambiguous non-standard source identifiers require review. The verification level is always `METADATA_ONLY`: the API does not fetch publisher pages or prove that the cited passage actually entails the claim.
- Claim approval requires a current assessment with metadata-consistent citation and clear safety findings. PostgreSQL repeats the version/current-rights and approval checks so an HTTP-only check is not the only guard. Suggested grades never auto-approve. The approver supplies the final A–D grade on the claim decision; a separate reasoned safety decision can clear a heuristic flag, but cannot waive citation mismatches or stale source rights. Release creation/evaluation also requires the latest matching source/right-version assessment, includes that assessment and version in the content fingerprint, and rejects an older assessment after source metadata or rights change.
- Extraction candidate screening and release evaluation share a conservative prompt-injection detector. Its adversarial regression corpus covers instruction overrides, jailbreak/role markup, shell/SQL/tool abuse, secret/data exfiltration, Unicode full-width and zero-width characters, punctuation obfuscation, and benign research text. The scanner stores finding codes, not matched raw excerpts, and flagged items require review; false negatives and false positives remain possible.

## Research release approval, version history, supersession and rollback

- Promoted release content and evaluation rows remain immutable. A tenant-scoped active channel points to the currently served version for each release key and advances a monotonic channel revision for concurrency checks.
- Promotion requires the current source/right-version-bound claim assessments, consistent citations, allowed source rights, safety clearance, a passing immutable contract evaluation with a matching fingerprint, a reviewer safety summary and external regression-evidence reference. The transition records `PROMOTED` and (when applicable) `SUPERSEDED` events atomically with the active-channel update and outbox event.
- Rollback changes only the active pointer; it does not edit or delete the current or historical release. It appends `ROLLBACK_FROM` and `ROLLBACK_TO` records with actor, reason, request and trace references. The target must be an older, already-promoted version of the same key, remain eligible under current claim/source rights and safety checks, and retain a passing evaluation whose fingerprint matches current calculated content. A stale target is rejected rather than silently trusted or rewritten.
- The database enforces sequential per-key tenant version numbers, the active target's tenant/key/status and current evidence rights, actor scope, channel revision increments and append-only lifecycle events under forced tenant RLS. Existing promoted records are labelled `BASELINE_IMPORTED`; pre-migration events or timestamps are not fabricated.

## Growth API

The factory-scoped endpoints are under `/growth`:

- `POST /opportunities` records a proposed growth hypothesis with assumptions, expected-value range, uncertainty, constraints snapshot, affected CBB nodes and at least one typed evidence item.
- `GET /opportunities` and `GET /opportunities/:opportunityId` return scoped opportunities and their evidence, scenarios, experiments and outcome history.
- `POST /opportunities/:opportunityId/decision` accepts/rejects proposed opportunities. Acceptance requires evidence and a success hypothesis.
- `POST /opportunities/:opportunityId/scenarios` stores an immutable, data-vintaged scenario run with deterministic `factoryos.growth.financial-sensitivity.v1` formula outputs and an input SHA-256 fingerprint. It only runs for accepted/in-progress opportunities. Its `constraintGate` is `REVIEW_REQUIRED` if any source-backed capacity/quality/cash/delivery limit or projected value is missing, `BLOCKED` if a limit is breached, and `PASS` only when all four checks pass. The database independently rejects a claimed `PASS` unless the saved opportunity snapshot, projected inputs, checks and attached evidence references agree; only then is generated `decision_ready` true.
- `POST /opportunities/:opportunityId/experiments` creates a controlled plan with owner, objective, hypothesis, leading indicators, duration, baseline and stop conditions. `POST /experiments/:experimentId/start` starts it; `POST /experiments/:experimentId/results` records pre/post measurements and evidence.
- `GET /opportunities/:opportunityId/scenario-comparison` compares up to 100 immutable scenario snapshots, exposes missing `BASE`/`UPSIDE`/`DOWNSIDE`/`STRESS` coverage and refuses to rank mismatched model versions, baselines or data vintages. Ranking is enabled only if all scenarios pass the database-enforced constraint gate; the response labels the result deterministic sensitivity, not a forecast or causal estimate.
- Each `growth_experiment_result` can be attached to at most one realised opportunity outcome, and the database enforces that the outcome belongs to the same opportunity as its source experiment. This prevents replayed requests or direct SQL writes from multiplying one experiment result into multiple learning signals.
- `POST /opportunities/:opportunityId/outcomes` records evidence-backed realized results, advances a qualifying in-progress hypothesis to `REALIZED`, and atomically appends an immutable `FACTORY`-scoped `ai_learning_signals` record linked to that exact outcome. The recorded confidence is explicitly submitter-assessed, not a calibrated causal probability. Both the outcome and learning-signal event are emitted through the transactional outbox.

Evidence origin is explicit: external research, client-private CBB, operational data, market signals or client documents. Research evidence must reference an approved rights-cleared research claim. Client-private evidence is stored only in the tenant/factory scope.

## Consistency and safety properties

- Every research/growth table has PostgreSQL RLS enabled and forced.
- Research claims cannot be approved until their source is currently approved, reuse rights are documented, a precise citation locator and evidence grade exist, and a current immutable evidence assessment finds the citation metadata consistent and safety screening clear.
- Ingestion jobs require a current approved source, a documented permitted rights basis and an unchanged source/rights version. If a source's access is revoked/rejected, its license becomes restricted/unknown, or full-text storage permission is withdrawn, the PostgreSQL trigger purges any stored claim excerpts in the same transaction and records only their SHA-256 digests, claim/source references, version numbers and purge reason in an immutable tenant-scoped audit table. A separate database trigger also clears `full_text_storage_allowed` whenever source access is not currently approved or the documented license basis is no longer permitted; a check constraint prevents that flag from being re-enabled in an invalid state. Pre-existing source rows without a rights history receive an explicitly labelled `BASELINE_IMPORTED` snapshot during migration. Full-text mode and excerpt persistence require the explicit full-text-storage flag. Rights/source updates atomically block queued, paused or running jobs; historical rights snapshots and job event timelines are append-only under forced tenant RLS.
- Extracted claims carry a locator and explicit extraction-item/run lineage. The output digest is computed by the API over a canonicalized extraction manifest; the fetched input digest is reported by the worker and is retained as worker-attested provenance, not described as independently re-hashed by this API because raw source bodies are not stored or submitted to the API.
- Extractor output is untrusted. The shared prompt-control/data-exfiltration scanner flags a reviewed adversarial test corpus, but remains a heuristic; it does not guarantee detection of all malicious instructions or replace an external security/regression evaluation.
- Knowledge releases can only promote with a stored PASSED evaluation bound to that exact release, unchanged claim/source fingerprint, approved visible claims, complete citation coverage, permitted rights, reviewer safety attestation and a recorded external regression-evidence reference. Promoted releases are also removed from tenant-visible release listings whenever any linked claim is superseded or its source loses currently approved reuse rights; immutable historical release rows are retained rather than rewritten. Evaluation records and promoted releases cannot be edited or deleted. The deterministic safety screen is a conservative signal, not a replacement for a security review or model-level regression suite.
- Growth opportunity evidence is append-only. Acceptance fails at the database boundary if evidence is missing; an opportunity cannot be marked realized without an outcome row.
- Scenario snapshots, experiment results and outcome evidence are append-only. Scenario input snapshots include data vintage, model version, projected constraint metrics and a SHA-256 fingerprint. A scenario without all four sourced constraint dimensions cannot become decision-ready, and every constraint reference must match evidence attached to that opportunity.
- Uncertainty ranking is deterministic, visible and auditable. Resolved unknowns require a resolution evidence reference, and the database prevents rewriting the question, impact or effort after the result is known.
- Opportunity, experiment and scenario writes are factory-authorized via IAM and emit transactional outbox events; writes are audited separately through the platform audit service.
- The sensitivity engine is deterministic arithmetic, not an AI forecast or causal model. It explicitly discloses the assumptions it uses.

## IAM permissions

The API permission catalog defines `research.read/write/review/ingest` and `growth.read/write/review`. Migration `134_research_ingestion_provenance.sql` registers the distinct `research.ingest` worker permission but does not automatically grant it to production roles. Assign `research.write` to source registrars, `research.review` to rights reviewers, `research.read` to consumers, and `research.ingest` only to the trusted worker identity permitted to claim jobs and persist extraction output. Production role grants remain explicit; the local development seed does not imply that a production role has this worker permission.

## Explicit remaining gaps before claiming full SRS completion

The backend now supplies the rights-gated ingestion queue, source/rights revision history, leases/checkpoints/retries, immutable worker events and extraction-run/item provenance contracts. It does **not** itself run a hosted DOI/publisher crawler, fetch arbitrary URLs, parse/OCR uploaded files or invoke an LLM/extraction provider; a deployed worker or provider adapter must consume the queue and call the worker endpoints. The input digest is worker-attested unless a future connector supplies verifiable artifact bytes to a trusted hashing boundary.

Still separate work includes provider-specific crawling and retry policy, customer-file upload/storage/parser integration, a production prompt-injection classifier beyond the heuristic adversarial corpus, source deduplication using similarity signals across DOI/preprint/journal versions, research search/embedding index, remote citation-content/semantic entailment benchmarks and calibration of the deterministic evidence rubric against expert-labelled datasets, global corpus curation tools, scheduled freshness monitoring, and end-to-end release/recommendation regression/evaluation suites. Growth-side gaps also remain: automated claim extraction is now persisted when a worker submits output, but no autonomous extractor is launched by this API; CBB/finance/order adapters do not yet auto-populate all authoritative business constraints, and multi-model scenario reasoning, instrumented experiments and production dashboards/SLO/DR evidence remain separate integrations. The existing release evaluator stores a contract-evaluation result but does not prove model-answer quality or execute a full benchmark by itself.

## Growth opportunity governance — assumptions, constraints, missing evidence and decision ownership

Migration `143_growth_opportunity_governance.sql` makes the opportunity's decision basis explicit instead of keeping all four dimensions only in free-text JSON.

### Governance API

All paths below are under `/api/growth` and require the authenticated tenant/factory scope.

| Method and path | Permission | Purpose |
|---|---|---|
| GET `/opportunities/:opportunityId/governance` | `growth.read` | Returns assumptions with their latest review, the latest constraint snapshot per dimension, open/resolved evidence gaps, owner assignment history, and a deterministic readiness checklist. |
| POST `/opportunities/:opportunityId/assumptions` | `growth.write` | Adds an immutable assumption with risk-if-false, submitter confidence, validation method, evidence references, owner and whether it blocks the decision. |
| POST `/opportunities/:opportunityId/assumptions/:assumptionId/decision` | `growth.review` | Appends `VALIDATED`, `REFUTED`, `DEFERRED` or `NEEDS_EVIDENCE`; validation/refutation must cite evidence already attached to the same opportunity. |
| POST `/opportunities/:opportunityId/constraints` | `growth.write` | Appends a dimensioned limit/observed-value record, units, source reference and source vintage, or a reasoned `NOT_APPLICABLE` decision. |
| POST `/opportunities/:opportunityId/evidence-gaps` | `growth.write` | Records a specific unknown, the evidence required to close it, impact, due date, owner and decision-blocking flag. |
| POST `/opportunities/:opportunityId/evidence-gaps/:gapId/decision` | `growth.review` | Appends gap lifecycle decisions `IN_REVIEW`, `RESOLVED`, `WAIVED` or `REOPENED`; resolution requires opportunity-attached evidence. |
| POST `/opportunities/:opportunityId/decision-owners` | `growth.review` | Assigns/reassigns `DECISION_OWNER`, `BUSINESS_OWNER`, `FINANCE_REVIEWER`, `OPERATIONS_REVIEWER`, `QUALITY_REVIEWER`, `RISK_REVIEWER` or `EVIDENCE_OWNER`. |

### Required decision controls

- **Assumptions are hypotheses, not facts.** Existing assumption strings are imported as unvalidated, high-risk governance records. A blocking assumption needs a latest `VALIDATED` decision supported by opportunity-attached evidence. `REFUTED`, `DEFERRED` and `NEEDS_EVIDENCE` remain visible in history but cannot satisfy the acceptance gate.
- **Constraints are explicit, versioned records.** Before acceptance, the latest entry for each core dimension—capacity, quality, cash and delivery—must state either `APPLICABLE` with an operator, threshold, observed value, unit, source evidence and as-of timestamp, or `NOT_APPLICABLE` with a reason. `MAX` passes only when observed value is at or below its threshold; `MIN` passes only at or above; `EQUALS` requires equality at stored precision. A source-backed record is still a blocker if its value violates the limit. `UNKNOWN`, missing measurements, missing source references and future source timestamps are not silently treated as a pass. New records supersede earlier observations without rewriting their history.
- **Missing evidence is tracked as work.** A gap states the question, required evidence, impact, owner, optional due date and whether it blocks a decision. A blocking gap must have the latest state `RESOLVED` with evidence, or a reasoned `WAIVED` decision. A resolved gap without references is rejected. Reopened gaps block readiness again.
- **Decision ownership is separate from authorship.** A named active `DECISION_OWNER` is mandatory and must be different from the opportunity creator. Only that active owner can accept or reject the hypothesis; the selected owner, actor, reason, readiness snapshot and request/trace references are recorded in append-only decision history. Reviewer role permissions still gate the HTTP commands.
- **One gate at both layers.** `GET .../governance` reports `READY` or `BLOCKED` with stable blocker codes and missing-evidence details. The service rejects an acceptance that is not ready, and PostgreSQL independently re-checks evidence, assumption review, the latest core constraints, blocking gaps, actor identity and decision-owner assignment in the state-transition trigger. Rejected proposals can still be rejected by the named decision owner when the evidence is insufficient.
- **Scoped and auditable.** Governance tables use forced tenant RLS and composite tenant/factory/opportunity foreign keys. Assumption definitions, constraint snapshots and gap definitions are immutable; assumption decisions, gap events and decision history are append-only. Mutations produce outbox events and audit records. Owner changes close the previous assignment and preserve its history.
- **Conservative semantics.** Readiness is a deterministic completeness/control check, not a forecast, probability, legal conclusion or approval by itself. `NOT_APPLICABLE` is an explicit reviewer-owned decision and should not be used to avoid measuring a real constraint. Constraint sources are manually/adapter-supplied today; this slice does not automatically connect every ERP, finance, quality or delivery system.
